## 3. 选型结论

- **首选 PaddleOCR**：唯一同时满足「中文公文质量最高（含版面/表格/方向）+ Apache-2.0 干净 + CPU 可跑 + star 最高」。
  代价：paddlepaddle 依赖重、模型数百 MB、需独立 venv 与常驻进程。
- **保底 RapidOCR**：Apache-2.0、只依赖 onnxruntime+opencv、模型 10–20MB、CPU 秒级、维护活跃。
  它跑的就是 PP-OCR 转 ONNX 的模型 ⇒ 质量继承主线，只是默认 mobile 模型略低于 PP-OCRv6 server。
- **不选 Surya**：权重是修改版 OpenRAIL-M（非 OSI、商用有营收门槛）⇒ 直接违反「许可证必须 OSI」硬约束；
  且生产需 GPU/llama.cpp。

**为什么两档都要**：本机（宝塔 CentOS + py3.13）已自带 `onnxruntime` ⇒ RapidOCR 零额外系统依赖即可跑；
paddlepaddle 的 CPU wheel 兼容性尚未实测。两档共用**同一个 HTTP 契约**，切换只改环境变量与依赖文件。

## 4. 接缝设计（已实现）

```
WordPress(php-fpm)                        本机常驻服务（systemd, 只监听 127.0.0.1:8848）
├─ 登记成功 → ocr_status=pending         HTTP  ┌──────────────────────────────┐
├─ WP-Cron 20s 后 → zw_ocr_process ──────────▶ │ POST /ocr {path: 存储根内绝对路径} │
│                                             │  → 白名单校验(realpath 前缀)   │
├─ 结果写回 policy_source.ocr_*  ◀──────────── │  → 引擎识别 → JSON(text/conf/ms)│
└─ 详情页展示 + 「重新识别」      GET /health ◀─│ 引擎名/版本/模型就绪           │
                                              └──────────────────────────────┘
```

- **数据落点**：复用 `zw_policy_source`（唯一政策库），只增 OCR 专用列
  `ocr_text` / `ocr_confidence` / `ocr_ms` / `ocr_at` / `ocr_message`；
  复用既有 `ocr_status` 与 `extraction_method`（写 `ocr:engine@version`）。**绝不**写 `doc_name` / 正文生效面。
- **安全**：端点只允许回环/内网（`zw_ocr_validate_endpoint()`，双端校验）；服务端 `realpath` 前缀白名单 +
  扩展名白名单 + 20MB 上限；PHP 只传路径不传字节（不产生第二份临时文件、不 base64）；令牌可选（`X-TCPC-OCR-Token`，
  常量时间比较）；`0.0.0.0` 属配置错误，README 明写禁止。
- **异步与降级**：登记页**不同步等 OCR** —— 只置 `pending` + 排 WP-Cron 单次事件（20s）；
  失败写 `failed` + `ocr_message`（≤255 字，只写原因不写内容），详情页给「为什么失败 + 就地重试 + 下一步」；
  OCR 未启用/未迁移/无附件 ⇒ 静默跳过，**登记链路零阻断**。
- **不新增菜单**：OCR 设置挂在「收文台账 → `view=ocr`」，详情页每篇收文一个 OCR 卡片。
  原因：新增子页会改权限功能树 ID 集与「子页 slug 与登记表一致」这两条既有判据
  （主题 `test-receipt-permissions.php` 逐项断言 5 个 slug），而本单是纯插件任务、不改主题测试口径。
