## 4. 架构裁定建议（第二批前必须定）

**不要把「拟办/批示/传阅/催办/清退」做成状态机新状态。** 依据：

- `zw_policy_issue` 同时服务 AI 法务部的整改台账（`source_type≠incoming`），扩状态值会污染既有语义
  （`receipt-issues.php` 文件头已明写「不改变既有语义」）；
- 收文状态机只有 4 态（`未开始/办理中/已办结/归档` + 派生 `逾期`），是**按「一件事办到哪」**建模；
  而拟办/批示/传阅是**同一件事上的多条留痕**，天然是一对多。

**建议模型**（第二批候选，需 `tcpc-architect` 裁定 + 变更单）：

| 新表 | 字段（草案） | 语义 |
| --- | --- | --- |
| `zw_receipt_handle_log` | `id, receipt_id, action(suggest/instruction/urge), author_id, author_name, dept_key, content, created_at` | 拟办 / 批示 / 催办 —— **append-only 流水**，只增不改 |
| `zw_receipt_circulation` | `id, receipt_id, target_type(user/dept), target_id, read_at, note, created_at` | 传阅 / 签阅 —— 一人一行，`read_at` 空=未阅 |

- 归档盒号/年度：`zw_policy_source` 增 **2 列**（`archive_box_no` / `archive_year`），沿用既有「收文增量列」迁移范式；
- 页数：`zw_policy_source` 增 1 列 `page_count`；
- 全部新增走**同一迁移脚本**（`scripts/migrate-receipt-schema.php` 扩项），先 dry-run 再 execute；
- 铁律不变：不新建第二套政策库、不改政策源生效版本、附件仍走私有存储 + canonical 文件打开。

## 6. 明确不采纳

| 对象 | 为什么不采纳 |
| --- | --- |
| Java BPM 全家桶（Flowable / Activiti / O2OA 学生项目） | 与「WordPress 单栈 + 宝塔 php-fpm」根本冲突，引入即多运行时 + 多数据库 |
| 微服务 / 独立数据库（PostgreSQL、独立服务） | 同上；且与主题「单一政策库」口径冲突 |
| open-core 阉割版（OpenKM CE 仅二进制、Alfresco/LogicalDOC 记录管理在商业版） | 不是 100% 开源；且授权不清 |
| 无 LICENSE 项目（信呼 / OA-SYS / innmis 系列） | 默认版权保留，只能看功能不能抄代码 |
| DzzOffice / IBOS | 无收文模块；抄会引入第二套网盘与权限实现，违反 canonical 唯一 |
| 照搬第三方 UI | 用户明确「UI 与发文管理对齐」⇒ 样式基线只取**本仓发文模块**，不取外部项目视觉 |
