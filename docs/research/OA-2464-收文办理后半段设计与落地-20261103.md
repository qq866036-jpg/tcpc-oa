## 1. 设计裁定（为什么这样建）

| 需求 | 落点 | 为什么不是别的做法 |
| --- | --- | --- |
| 拟办意见 / 领导批示 / 催办 | 新表 `zw_receipt_handle_log`（append-only） | 不扩 `zw_policy_issue.status`：它同时服务法务整改台账，扩状态值会污染既有语义；而这三者是「同一件事上的多条留痕」，天然一对多 |
| 传阅 / 签阅 | 新表 `zw_receipt_circulation`，`(receipt_id,target_type,target_id)` 唯一 | 一人一行、签阅只写 `read_at` 一列；不用 user meta（跨人查询要 N 次）、不塞进 handle_log（签阅是**同一行的状态变化**，不是新增留痕） |
| 归档盒号 / 归档年度 / 页数 | `zw_policy_source` 增 3 列 | 属「这份来文」的固有属性，不是流水；纸质归档标识与私有存储目录（部委/年份）互不影响 |
| 紧急程度 4 档 | `zw_receipt_urgency_options()` 扩字典 | 保留历史取值 `加急`（展示为「加急（急件）」），避免存量被拆成两档；`一般`/`平件` 为新增 |
| 待批示角标 | 菜单标题气泡 + 台账顶部提示条 | 不新增子菜单（会改权限功能树 ID 集与「子页 slug 与登记表一致」判据）；气泡在 `add_menu_page` 之后改 `$GLOBALS['menu']`，不改调用本体（既有判据按「add_menu_page 块内出现 58.6」取源） |

**写规则（一票否决级）**：`handle_log` **只 INSERT**；`circulation` 只 INSERT + 签阅 UPDATE 一列；
`archive` 只 UPDATE 3 列且 `WHERE id = %s` 单行。全表无 DELETE、无批量 UPDATE。

## 2. 表结构

```sql
CREATE TABLE {prefix}zw_receipt_handle_log (
  id BIGINT UNSIGNED AUTO_INCREMENT,
  receipt_id VARCHAR(64) NOT NULL,          -- 收文记录 ID（SRC-…）
  action VARCHAR(16) NOT NULL,              -- suggest | instruction | urge
  author_login VARCHAR(64), author_name VARCHAR(64), dept_key VARCHAR(64),
  content TEXT,                             -- ≤5000 字（入库前截断）
  created_at DATETIME,
  PRIMARY KEY (id), KEY receipt_action (receipt_id, action), KEY action_created (action, created_at)
);

CREATE TABLE {prefix}zw_receipt_circulation (
  id BIGINT UNSIGNED AUTO_INCREMENT,
  receipt_id VARCHAR(64) NOT NULL,
  target_type VARCHAR(8) NOT NULL,          -- user | dept
  target_id VARCHAR(64) NOT NULL,           -- 登录名 / 部门 key
  read_at DATETIME NULL,                    -- 签阅时间（只写一次）
  note VARCHAR(255), created_by VARCHAR(64), created_at DATETIME,
  PRIMARY KEY (id), UNIQUE KEY receipt_target (receipt_id, target_type, target_id)
);

ALTER TABLE {prefix}zw_policy_source
  ADD COLUMN page_count SMALLINT UNSIGNED NULL,
  ADD COLUMN archive_box_no VARCHAR(64) NULL,
  ADD COLUMN archive_year SMALLINT UNSIGNED NULL;
```

迁移：`scripts/migrate-receipt-handle.php dry-run|execute|verify`（`dbDelta` 建表 + 逐列 ADD；幂等；缺表缺列一律可检出）。

## 3. 页面与入口

- **详情页**（`zw-receipt-ledger&view=detail&id=…`）新增 3 张卡片：
  1. **拟办与批示**：时间线表格（类型/人/时间/内容）+ 追加表单（类型下拉：拟办/批示/催办 + 内容必填）。
  2. **传阅与签阅**：登记列表（类型/对象/登记时间/签阅时间/备注/「签阅」按钮）+ 登记表单
     （对象类型 user|dept + 对象标识 + 备注）。
  3. **归档信息**：盒号 / 年度 / 页数 + 保存。
- **台账页**：待批示 >0 时顶部黄色提示条（可读入口，替代只有气泡的隐晦提示）。
- **左侧菜单**：`收文管理` 标题后挂 `awaiting-mod` 气泡（WordPress 原生待办样式）。
- 所有写入口走 `admin-post`（4 个 action），**能力位 `tcpc_perm_doc` + 按记录绑定 nonce**，
  成功/失败都回详情页并带 `zw_msg` 提示码（失败给原因，不只 toast）。

## 4. 与既有契约的关系（兼容性）

- **台账主查询 `zw_receipt_ledger_query()` SQL 一字未改**（主题契约面 + `test-receipt-ledger.php` 断言面）；
  归档信息用**独立小查询** `zw_receipt_handle_archive_info()`（与 OCR 的 `zw_ocr_record()` 同一套路）。
- 收文状态机不变（4 态 + 派生逾期）；拟办/批示**不**改变状态，办理仍走「收文办理」。
- 权限功能树 ID 集不变（无新子页）；菜单 position 58.6 与顺序不变。
